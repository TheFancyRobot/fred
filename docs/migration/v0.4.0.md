# Migrating to v0.4.0 HTTP workflows

Fred core remains transport-neutral. Do not add HTTP options to `createFred()`.
Enhance a core client explicitly with `withHttp()` from
`@fancyrobot/fred-http`.

## Expose workflows

Register workflows before the listener starts, then choose one exposure mode:

```ts
const core = await createFred();
await core.workflows.define(workflow);

// Expose every registered workflow with default paths and inherited auth.
const all = withHttp(core, { workflowEndpoints: true });

// Or use an explicit production allowlist.
const selected = withHttp(core, {
  workflowEndpoints: {
    report: { auth: { scopes: ['workflows:run'] } },
    status: { path: '/public/status', auth: false },
    progress: { stream: true, auth: { scopes: ['workflows:stream'] } },
  },
});
```

The default route is `POST /workflows/:id`. Input and completed-output OpenAPI
schemas derive from the workflow Schemas. Route generation snapshots the
workflow registry at `listen()`; restart the listener after adding or changing
workflows.

## Move production auth to scoped keys

The single development bearer token remains available for local use. For
production workflow routes, use the API-key store and create hash-only records
in durable storage:

```bash
fred keys create --sqlite ./fred.db --scopes workflows:run
# or: fred keys create --postgres "$DATABASE_URL" --scopes workflows:run
```

The raw key is emitted once after persistence. The server never recovers or
logs it. Point the CLI and HTTP server at the same store, rotate by issuing a
replacement, then revoke the old key.

## Review configuration

HTTP configuration is validated by `@fancyrobot/fred-http`. Set explicit CORS
origins, request body and timeout limits, persistent rate-limit storage, and
redaction paths. Leave proxy trust disabled unless a trusted deployment proxy
overwrites forwarded client-address headers.

See `examples/15-http-workflows` for a complete deterministic JSON/SSE project.
