# Phase 46.1: Refactor Examples to Use .md Agent Definitions & ETA Templates - Context

**Gathered:** 2026-03-03 (updated 2026-03-03)
**Status:** Ready for planning

<domain>
## Phase Boundary

Refactor all 12 examples to define agents via `.md` files with YAML frontmatter instead of inline programmatic `createAgent()` calls. Demonstrate ETA templating features (conditionals, loops, expressions, partials, env vars, per-message vars) across the example set where they fit naturally. No new examples are created; existing example behavior and learning path ordering are preserved.

</domain>

<decisions>
## Implementation Decisions

### Philosophy: declarative by default
- Configuration belongs in config.yaml and agent `.md` files, not in code
- Programmatic config is for advanced users who need custom runtime logic — examples should not default to it
- `.ts` code should be minimal: `Fred.create()`, `initializeFromConfig()`, register tools (runtime logic), process messages, shutdown
- The separation: agents are content (`.md`), tools are code (`.ts`), config is declarative (`config.yaml`)

### Default provider: OpenRouter free
- ALL 12 examples use OpenRouter as the provider with `openrouter/free` as the default model
- This allows users to test every example without spending money — only an OpenRouter API key is required
- Provider declaration lives in each example's `config.yaml`
- `.env.example` files updated to show `OPENROUTER_API_KEY`

### Migration completeness
- Full migration: ALL 12 examples define ALL agents using `.md` files with YAML frontmatter
- No `createAgent()` calls with inline system prompts remain in any example
- All agent config (tools, temperature, mcpServers, etc.) goes into `.md` frontmatter
- Intents (utterances) live in agent `.md` frontmatter — intents belong with the agent they route to
- Tool definitions (Effect Schema, handler functions) stay in `.ts` source files; registered via `fred.registerTool()` before `initializeFromConfig()`; `.md` frontmatter references tools by name via `tools: ['calculator', 'weather']`
- Hooks, pipeline config, and other runtime behavior stay in `.ts` source files

### Agent loading mechanism
- Every example has a `config.yaml` with provider declaration
- Each example calls `initializeFromConfig()` to enable agent auto-discovery
- If `./agents/` directory exists next to the config file, it is scanned automatically — no `agentDirs` field needed in config
- `Fred.create()` alone does NOT auto-scan for agent files; `initializeFromConfig()` is required

### ETA feature distribution
- Natural fit: each ETA feature goes into the example where it makes the most organic sense
- Plain markdown (no ETA) is acceptable for simple agents — no forced/artificial templating
- Each of the 6 ETA features (conditionals, loops, expressions, partials, env vars, per-message vars) must appear at least once across the full 12-example set
- Per-example partials directories (not shared top-level) — preserves self-contained packaging model

### Agent file organization
- `agents/` directory at each example root (e.g., `examples/01-quickstart-single-agent/agents/assistant.md`)
- Matches Phase 45.1 default convention of `./agents/`
- Flat directory structure within `agents/` — no subdirectories even for examples with multiple agents
- Filenames match frontmatter `id` (e.g., `billing-support.md` has `id: billing-support`)
- `partials/` directory at example root when partials are needed (self-contained per example)

### Example-specific treatment
- **Example 09 (eval harness)**: Full eval loop — `.md` agent as test target, live API calls (always-live evals, not pre-recorded traces). `src/index.ts` is the app (create Fred, process message). `test/eval.test.ts` runs eval assertions against same agents with live API. `bun test` is the single eval entry point — no standalone eval runner script.
- **Example 10 (config-driven)**: Both config.yaml and programmatic-equivalent.ts share the same `agents/` directory with `.md` files; programmatic-equivalent.ts serves as a "Rosetta Stone" showing config-to-code mapping for advanced users
- **Example 12 (CLI/TUI)**: Existing `config.yaml` already handles agent loading; agent definitions move to `.md` files (no `agentDirs` needed — `./agents/` auto-discovered)

### Claude's Discretion
- Which specific ETA feature maps to which example — distribute for coverage while keeping usage natural
- Per-message dynamic variable approach (real Fred variables vs simulated setGlobalVariable()) — pick the most illustrative approach per example
- README updates to explain the .md agent format within each example

</decisions>

<specifics>
## Specific Ideas

- Tool/agent separation: tools are code (schema + handler in .ts), agents are content (prompt + config in .md) — this makes the .md format feel like the "right" place for agent definitions
- Example 10's programmatic equivalent becomes a "Rosetta Stone" showing how config.yaml + .md agents maps to programmatic API calls — this is the advanced user reference
- Example 09 with a test-target agent shows the most compelling dev workflow: write agent prompt in .md, write eval tests with live API, iterate
- Intents as frontmatter: agents declare their own routing triggers (utterances) rather than intents being registered separately — keeps routing logic co-located with the agent

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `packages/core/src/agent/file-loader.ts`: Complete `.md` agent parsing with frontmatter validation (id, platform, model required)
- `packages/core/src/template/engine.ts`: ETA template engine with security restrictions, strict undefined handling, partial support
- `packages/core/src/template/validate.ts`: Template validation utilities (compileTemplate, resolveAgentTemplate, securityLintTemplate)
- `packages/core/src/agent/file-watcher.ts`: Hot reload with debounced change detection

### Established Patterns
- Agent frontmatter supports all AgentConfig fields: tools, temperature, maxTokens, utterances, mcpServers, toolChoice, toolRetry, vars
- ETA context model: `{ vars, env, config, agent }` — vars from frontmatter, env from filtered allowlist, agent from resolved config
- Two-phase resolution: frontmatter resolves at load time, body resolves per-message
- Files without frontmatter delimiters are silently skipped (plain .md files are not auto-registered)

### Integration Points
- `initializeFromConfig()` auto-discovers `./agents/` directory relative to config file — no explicit `agentDirs` needed if convention followed
- `fred.registerTool()` in code + `tools: ['tool-name']` in frontmatter — tool registration separate from agent definition
- Each example needs a `config.yaml` (provider declaration + any non-agent config) for `initializeFromConfig()` to work
- Guard test (`tests/unit/examples/examples-guard.test.ts`) validates structure, imports, and compile checks

</code_context>
