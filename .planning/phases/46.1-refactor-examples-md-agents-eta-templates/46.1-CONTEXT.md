Refactor all 12 examples to define agents via `.md` files with YAML frontmatter instead of inline programmatic `createAgent()` calls. <decisions>
## Implementation Decisions

### Migration completeness
- Full migration: ALL 12 examples define ALL agents using `.md` files with YAML frontmatter
- No `createAgent()` calls with inline system prompts remain in any example
- All agent config (tools, temperature, utterances, mcpServers, etc.) goes into `.md` frontmatter
- Agents are discovered automatically from `agentDirs` at startup — no programmatic agent creation
- Tool definitions (Effect Schema, handler functions) stay in `.ts` source files; `.md` frontmatter references tools by name via `tools: ['calculator', 'weather']`
- Example 10 (config-driven-yaml) keeps its programmatic-equivalent.ts as a reference, but both the config-driven and programmatic paths share the same `.md` agent files

### ETA feature distribution
- Natural fit: each ETA feature goes into the example where it makes the most organic sense
- Plain markdown (no ETA) is acceptable for simple agents — no forced/artificial templating
- Each of the 6 ETA features (conditionals, loops, expressions, partials, env vars, per-message vars) must appear at least once across the full 12-example set
- Per-example partials directories (not shared top-level) — preserves self-contained packaging model

### Agent file organization
- `agents/` directory at each example root (e.g., `examples/01-quickstart-single-agent/agents/assistant.md`)
- Matches Phase 45.1 default convention of `./agents/`
- Flat directory structure within `agents/` — no subdirectories even for examples with multiple agents
- Filenames match frontmatter `id` (e.g., `billing-support.md` has `id: billing-support`)
- `partials/` directory at example root when partials are needed (self-contained per example)

### Example-specific treatment
- **Example 09 (eval harness)**: Gets a `.md` agent as the test target — demonstrates the full loop of define-agent-in-.md then test it with golden traces
- **Example 12 (CLI/TUI)**: Existing `config.yaml` gets `agentDirs: ['agents']` added; agent definitions move to `.md` files
- **Example 10 (config-driven)**: Both config.yaml and programmatic-equivalent.ts share the same `agents/` directory with `.md` files

### Claude's Discretion
- How each example loads .md agents (config.yaml agentDirs vs programmatic initialization) — pick the cleanest approach per example
- Which specific ETA feature maps to which example — distribute for coverage while keeping usage natural
- Per-message dynamic variable approach (real Fred variables vs simulated setGlobalVariable()) — pick the most illustrative approach per example
- README updates to explain the .md agent format within each example

</decisions>

<specifics>
## Specific Ideas

- Tool/agent separation: tools are code (schema + handler in .ts), agents are content (prompt + config in .md) — this makes the .md format feel like the "right" place for agent definitions
- Example 10's programmatic equivalent becomes a "Rosetta Stone" showing how config.yaml + .md agents maps to programmatic API calls
- Example 09 with a test-target agent shows the most compelling dev workflow: write agent prompt in .md, write eval tests, iterate

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `packages/core/src/agent/file-loader.ts`: Complete `.md` agent parsing with frontmatter validation (id, platform, model required)
- `packages/core/src/template/engine.ts`: ETA template engine with security restrictions, strict undefined handling, partial support
- `packages/core/src/template/validate.ts`: Template validation utilities (compileTemplate, resolveAgentTemplate, securityLintTemplate)
- `packages/core/src/agent/file-watcher.ts`: Hot reload with debounced change detection

### Established Patterns
- Agent frontmatter supports all AgentConfig fields: tools, temperature, maxTokens, utterances, mcpServers, toolChoice, toolRetry, vars
- ETA context model: `{ vars, env, config, agent }` — vars from frontmatter, env from filtered allowlist, agent from resolved config
- Two-phase resolution: frontmatter resolves at load time, body resolves per-message
- Files without frontmatter delimiters are silently skipped (plain .md files are not auto-registered)

### Integration Points
- `agentDirs` config field in FrameworkConfig — examples use this to specify `['agents']`
- `initializeFromConfig()` automatically discovers and loads .md agents from configured dirs
- `fred.registerTool()` in code + `tools: ['tool-name']` in frontmatter — tool registration separate from agent definition
- Guard test (`tests/unit/examples/examples-guard.test.ts`) validates structure, imports, and compile checks

</code_context>
