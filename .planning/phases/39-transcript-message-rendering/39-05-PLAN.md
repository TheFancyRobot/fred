TWO changes addressing diagnosed root causes:

**Fix 1: Calculator tool schema — additionalProperties:false**

The debug session confirmed that Effect's JSONSchema generator adds `additionalProperties: false` to the generated JSON Schema when tools use `Schema.Struct`. This field is not in the calculator's `metadata` object (which is what the AI sees as description), but it IS in the JSON Schema that `@effect/ai` generates from the `Schema.Struct` definition and sends to the provider API. Some providers (especially non-OpenAI ones) may silently reject tool definitions with `additionalProperties: false`.

The calculator tool at `packages/core/src/tool/calculator.ts` already has `strict: false` (line 276). Check how `factory.ts` uses the `strict` field — if `strict: false` means it should NOT apply strict-mode transformations (including `additionalProperties: false`), verify that `transformFieldsForStrictMode` still runs regardless. The `strict` flag on the tool controls whether OpenAI strict-mode is used.

The actual fix: In `factory.ts`, when building `EffectTool.make` for tools, `@effect/ai` internally calls `JSONSchema.make()` on the Effect Schema, which adds `additionalProperties: false` at the struct level. We cannot easily control this from our side. Instead, the fix is to ensure the system prompt does not redundantly describe the calculator tool (which encourages XML hallucination), and to add the XML filter (Fix 2) as a defense layer.

Review the `packages/dev/src/chat-defaults.ts` system prompt (lines 56-59). It currently says "You have access to a calculator tool" — this primes smaller models to generate `<calculator>` XML tags. If the system prompt can be simplified to not mention specific tool names (the model already receives tool definitions via the API), consider removing the explicit calculator mention. However, keep the "Do not generate text that looks like XML tags" instruction.

**Fix 2: Broaden XML filter in output.ts**

In `packages/core/src/stream/output.ts` at line 69, the current pattern is:
```typescript
const xmlToolCallPattern = /<(?:function|tool)[^>]*>.*?<\/(?:function|tool)>/gi;
```

This only matches `<function>` and `<tool>` tags. Broaden it to match any XML-style pseudo-tool-call pattern, including tool-name-based tags like `<calculator>`:

```typescript
const xmlToolCallPattern = /<(?:function|tool|[a-z][a-z0-9_-]*)[^>]*>[\s\S]*?<\/(?:function|tool|[a-z][a-z0-9_-]*?)>/gi;
```

This matches:
- `<function>...</function>` (existing)
- `<tool>...</tool>` (existing)
- `<calculator>...</calculator>` (new)
- `<any_tool_name>...</any_tool_name>` (new — catches any lowercase tag that looks like a tool call)

Use `[\s\S]*?` instead of `.*?` to handle multi-line XML blocks.

Note: This broader pattern could theoretically match legitimate XML/HTML in model responses. This is acceptable because:
1. The TUI renders markdown, not HTML — HTML tags in assistant responses are not useful
2. Tool-calling models rarely produce legitimate XML in conversational responses
3. The filter only applies to streaming output display, not to stored message content

<task type="auto">
  <name>Task 2: Add XML filtering in TUI chat.ts token path</name>
  <files>packages/cli/src/commands/chat.ts</files>
  <action>
The TUI chat event loop at `packages/cli/src/commands/chat.ts` lines 256-257 pushes ALL token deltas directly to display without any filtering:

```typescript
if (event.type === 'token' && event.delta) {
  app.pushAssistantToken(event.delta, 1);
}
```

The `streamOutput` utility in `output.ts` has XML filtering, but the TUI path does not use it. Add inline XML filtering before pushing token deltas to the TUI.

**Implementation:**

Add a token accumulation buffer and XML-aware filtering. The challenge is that XML tags may span multiple token deltas (e.g., `<calc` in one token, `ulator>` in the next). A simple per-token regex won't catch split tags.

Use a buffering approach:

1. Before the `for await` loop (around line 255), declare:
```typescript
let tokenBuffer = '';
const xmlTagPattern = /<\/?[a-z][a-z0-9_-]*[^>]*>/gi;
```

2. In the token handler, accumulate and flush:
```typescript
if (event.type === 'token' && event.delta) {
  tokenBuffer += event.delta;

  // Check if buffer might contain a partial opening XML tag
  const lastOpenBracket = tokenBuffer.lastIndexOf('<');
  if (lastOpenBracket >= 0) {
    const afterBracket = tokenBuffer.slice(lastOpenBracket);
    // If we have an unclosed tag, hold it in the buffer
    if (!afterBracket.includes('>')) {
      // Flush everything before the potential tag
      const safe = tokenBuffer.slice(0, lastOpenBracket);
      if (safe) {
        app.pushAssistantToken(safe, 1);
      }
      tokenBuffer = afterBracket;
      continue; // Wait for more tokens to complete the tag
    }
  }

  // No partial tags — filter complete XML tags and flush
  const filtered = tokenBuffer.replace(
    /<\/?[a-z][a-z0-9_-]*[^>]*>[\s\S]*?(?:<\/[a-z][a-z0-9_-]*>)?/gi,
    ''
  );
  if (filtered) {
    app.pushAssistantToken(filtered, 1);
  }
  tokenBuffer = '';
}
```

3. After the `for await` loop completes (before `app.completeAssistantStream()` at line 287), flush any remaining buffer:
```typescript
// Flush any remaining buffered tokens (in case a partial tag was never closed)
if (tokenBuffer) {
  app.pushAssistantToken(tokenBuffer, 1);
  tokenBuffer = '';
}
```

**IMPORTANT:** This filtering is a defense layer for when models hallucinate XML-style tool calls. It does NOT replace proper tool calling — it just prevents raw XML from appearing in the TUI when a model generates text like `<calculator> 7 * 7</calculator>` instead of using native API tool calling.

Keep the approach simple. If the buffering logic becomes too complex, a simpler alternative is acceptable: just apply the regex to each delta individually. This won't catch tags split across deltas but will handle the common case where the entire XML tag arrives in one or two tokens. The key improvement is filtering SOMETHING rather than the current behavior of filtering NOTHING.
