# Phase 45.2: Implement ETA for Templating Agent Prompts and Frontmatter - Context

**Gathered:** 2026-03-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the existing simple `{{ var }}` template substitution system with ETA (a lightweight JavaScript templating engine) for processing agent prompts and frontmatter values. All agent sources (`.md` files, JSON/YAML config, programmatic `createAgent()`) get unified ETA processing. The old `resolveTemplate()` system is removed entirely. This is part of the v0.3.0 breaking change milestone.

</domain>

<decisions>
## Implementation Decisions

### Template Syntax & Capabilities
- Full ETA feature set: conditionals (`<% if %>`), loops (`<% for %>`), expressions (`<%= %>`), and partials (`<%~ include() %>`)
- Standard ETA delimiters (`<% %>`) — no custom delimiters
- ETA processes BOTH the markdown body (system prompt) AND frontmatter values — enabling dynamic config like `model: <%= env.MODEL %>`
- Partials supported with a dedicated partials directory for prompt composition via `<%~ include('shared/safety-rules') %>`
- Sync rendering only — no async operations inside templates; all data is pre-resolved before ETA runs
- No auto-escaping — prompts go to AI models, not browsers
- Template compilation errors (syntax errors) fail at startup — caught immediately during agent loading, before any messages are processed

### Variable Scope & Data Model
- Rich structured context object available inside templates: `{ vars: globalVars, env: filteredEnv, agent: { id, model, ... }, config: fredConfig }`
- Environment variables exposed via a filtered allowlist — prevents accidental secret leakage into AI prompts. Research needed: investigate best practices from similar projects for allowlist implementation. Thorough documentation required explaining how env filtering works
- Frontmatter supports a `vars:` block for per-agent custom variables (like Jekyll page variables), available in the template body
- Existing `VariableFactory` pattern integrates: factory outputs resolve before ETA runs and appear in the `vars` namespace
- Plugin-style extensible context: users can register custom context namespaces beyond the built-in ones (e.g. `fred.addTemplateContext('db', () => dbStats)`)
- ETA expressions ARE supported in frontmatter values, but cannot reference the current agent's own config (no circular/self-referencing)

### Resolution Timing & Caching
- Two-phase resolution: frontmatter resolves at load time (config is fixed), body resolves per-message (prompt is dynamic)
- Per-message body resolution ensures dynamic variables (time, counters) always reflect current state
- Configurable strictness: strict mode throws on undefined variables (good for CI/prod), lenient mode uses empty string (good for dev) — configurable per-agent or globally
- Hot reload from Phase 45.1 triggers auto-recompile of the ETA template — file change invalidates compiled function, next message uses new template
- Partial file changes also trigger recompile for all agents that include that partial — full hot reload chain

### Migration & Compatibility
- ETA replaces the `{{ var }}` system entirely — clean break, no dual template engines
- `resolveTemplate()` in `variables/template.ts` is removed (fits v0.3.0 "no backward-compat shims" philosophy)
- All agent prompt sources are processed through ETA uniformly (`.md` files, config agents, programmatic agents)
- Programmatic `createAgent()` uses auto-detection: if systemMessage contains `<% %>` tags, run through ETA; otherwise pass through unchanged
- Example updates deferred to Phase 46 (Showcase Examples & Framework Differentiation)

### Error Handling & Debugging
- Template runtime failures (undefined property access, type errors) fail the message with a clear error — no silent degradation or fallback to raw template
- Source-mapped errors: error messages include the .md file path and approximate line number where the error occurred
- Typed Effect errors: `TemplateResolutionError` with cause, filePath, and expression — callers handle with `Effect.catchTag`

### Partials Organization
- Configurable via `partialDirs` config option, default to top-level `./partials/` directory
- Referenced by relative path without extension: `<%~ include('safety/rules') %>` maps to `partials/safety/rules.md`
- Partials inherit the full template context from the including template (same vars, env, agent, config)

### Security
- Restricted globals: dangerous globals (require, process, fs) removed from template scope — templates can only access the provided context object
- Optional sanitization helpers available in template context (e.g. `<%= sanitize(userInput) %>`) — authors opt in
- Configurable maximum template output size limit — prevents runaway loops or include chains from generating massive prompts
- Short configurable execution timeout — catches infinite loops in template code

### Testing & Validation
- CLI validate command (e.g. `fred validate` or `fred template check`) that parses and compiles all agent templates without starting Fred — great for CI
- Validate command includes optional `--preview` flag to show resolved output with current variable values
- Validate includes security lint: flags templates that reference restricted globals or env vars outside the allowlist (warnings, not errors)
- Exported test utilities: functions like `compileTemplate()`, `resolveAgentTemplate()` available from @fred/core for users to call in their own test suites

### Claude's Discretion
- Agent namespace scope — what AgentConfig fields are exposed in the `agent` context
- Template compile caching strategy (compile-once vs other approaches)
- Partial nesting rules (depth limits, recursion prevention)
- ETA opt-out mechanism (whether `template: false` or similar is needed)
- Whether frontmatter `vars:` values themselves support ETA expressions
- Preview/debug tooling beyond the validate command
- Exact env var allowlist pattern and configuration mechanism
- Error message formatting details
- Sanitization helper implementations

</decisions>

<specifics>
## Specific Ideas

- Env var allowlist needs research into how similar projects handle this — document the approach thoroughly so users understand what's exposed and what's filtered
- Two-phase resolution is key: frontmatter produces config (fixed at load), body produces prompt (dynamic per-message) — different lifecycles
- Auto-detect for programmatic agents means zero config for simple cases — ETA syntax presence triggers processing
- The validate command with `--preview` flag gives developers a complete debugging story without needing to start Fred

</specifics>

### Integration Points
- `AgentFactory.resolveSystemMessage()` at factory.ts:826 — primary replacement point
- `AgentService.setGlobalVariablesResolver()` — may need ETA-aware equivalent
- `loadAgentFiles()` in file-loader.ts — frontmatter template processing happens here (load-time resolution)
- `AgentFileWatcher` change handler — triggers recompile of cached ETA functions
- Fred class `globalVariables` and `snapshotGlobalVariablesSync()` — feeds the `vars` namespace
