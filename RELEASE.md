# Fred release runbook

Fred releases all publishable workspaces together while preserving each
package's independent major version line. `MIGRATION.md` is the canonical
candidate compatibility matrix.

## Release candidate

1. Start from a clean checkout and frozen install.
2. Run `bun run build`, `bash scripts/build-declarations.sh`, `bun test`, and
   `bun run docs:build`.
3. Inspect `.changeset/pre.json`. If it exists, continue with its recorded
   prerelease tag and do not re-enter prerelease mode. If it does not exist,
   enter the selected tag (normally `alpha` or `rc`) before versioning:

   ```bash
   bunx changeset pre enter alpha
   bun run ci:version
   ```

   Re-run the gates after versioning. In an existing prerelease cycle, do not
   infer the suffix from a package's new semver line: Changesets increments the
   recorded prerelease counter. Read every exact candidate from the versioned
   manifests. For the current plan, one pass produces CLI `0.6.0-alpha.1`.
4. Update the exact versions in `MIGRATION.md`, the repository README, and all
   package README install snippets if manifests changed. No documentation pin
   may name an earlier prerelease artifact while describing the new candidate.
5. Publish with `bun run ci:publish`. `scripts/publish-packages.sh` reads
   `.changeset/pre.json` and passes `--tag <prerelease-tag>` to every publish,
   so a prerelease never moves npm's `latest` tag.
6. Verify every package/version with `npm view <package>@<version> version` and
   `npm view <package> dist-tags --json`.
7. Install the exact candidate versions into clean disposable Fred and Stanza
   consumers. Do not use workspace or `file:` resolution for registry proof.

The release workflow creates or updates the Changesets version PR on `main`.
Package changelogs are generated by `changeset version`; do not hand-edit
generated release entries before that step.

## Stable promotion

Stable promotion requires green clean-clone, package/tarball, documentation,
example, security, and Stanza validation plus explicit owner authorization.
Exit prerelease mode, version the final packages, repeat every gate, and publish
without a prerelease tag:

```bash
bunx changeset pre exit
bun run ci:version
bun run ci:publish
```

Confirm `latest` only after all package publishes succeed. If an `rc` tag is
used instead of the repository's current `alpha`, start that prerelease cycle
with `bunx changeset pre enter rc`; never relabel an unvalidated alpha as an RC.

Independent versions are expected. Do not force every package to `0.4.0` and
do not publish a partially compatible matrix as stable.

## Rollback

- Before stable promotion, leave `latest` unchanged and publish a corrected
  candidate under the prerelease tag.
- If a candidate tag points at a bad version, move only that prerelease
  dist-tag to the last validated version with
  `npm dist-tag add <package>@<version> <tag>`.
- If stable publication partially succeeds, stop. Do not republish or move
  remaining `latest` tags until the exact published state is recorded and the
  owner chooses forward-fix versus dist-tag restoration.
- npm versions are immutable. Never delete and recreate a version; publish a
  new patch/prerelease and update the compatibility matrix.
- For API-key incidents, preserve previous verifier/pepper configuration until
  active keys are migrated or revoked; package rollback does not recover a
  removed pepper.

Record the final package/version/dist-tag matrix in the release handoff.
